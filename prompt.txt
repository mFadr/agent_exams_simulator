# MASTER PROMPT: Build a Hybrid Local + API-Based AI Exam Simulator for Windows

## 1. Project Overview

Act as a senior software engineer, AI application architect, UX/UI designer, and educational technology specialist. Your task is to design and develop a complete, functional desktop application called **AI Exam Simulator**.

The application should simulate realistic exams and help students prepare for tests, entrance examinations, university assessments, professional certifications, and other academic evaluations.

The system must work using a **hybrid AI architecture** that combines local AI models running on the user's computer with cloud-based AI models accessed through an API key. It must remain useful even when the user has no API key, while providing enhanced capabilities when a cloud model is available.

The application should not simply generate questions and display scores. It should behave like an intelligent examination environment: creating realistic tests, monitoring the student's answers, evaluating responses, identifying weaknesses, explaining mistakes after the exam, and generating personalized practice plans.

Develop a real application, not just a concept, prototype, or collection of code snippets. Prioritize reliability, modularity, maintainability, privacy, and a professional user experience.

## 2. Target Platform and Technology Stack

Build the first version as a native desktop application for **Windows 10 and Windows 11**.

Use the following recommended technologies:

- **Programming language:** Python 3.11 or a compatible modern Python version.
- **Desktop interface:** PySide6, with a professional and responsive user interface.
- **Local AI inference:** Ollama, allowing users to run compatible local language models.
- **Cloud AI:** An API-based provider, preferably through a configurable OpenAI-compatible client.
- **Data storage:** SQLite for exam results, question banks, user settings, learning history, and performance statistics.
- **Data processing:** Python libraries suitable for document extraction, structured data validation, and report generation.
- **Optional mathematical evaluation:** SymPy or another reliable calculation tool when appropriate.
- **Optional document export:** PDF and CSV export, with support for additional formats where useful.

Keep the application modular so that the AI provider, model, database, document-processing components, and interface can be changed independently.

Do not hard-code a particular API provider as the only supported option. Make it possible to configure the provider, API endpoint, model name, and API key through settings.

## 3. Core Objective

The application must allow users to create, customize, take, and review simulated exams.

A typical workflow should be:

1. The user creates an exam or chooses a predefined exam template.
2. The user selects a subject, topics, difficulty, duration, number of questions, and question formats.
3. The system generates or selects a suitable question set.
4. The user starts the exam in a dedicated examination interface.
5. The application tracks answers, remaining time, question navigation, and completion status.
6. The user submits the exam, or the exam ends automatically when the time limit is reached.
7. The system evaluates the answers and calculates the result.
8. The user receives a detailed report showing strengths, weaknesses, mistakes, and recommended next steps.
9. The application can generate a targeted follow-up exam based on the user's performance.

Make the experience feel like a real exam, while also providing a strong learning environment before and after the examination.

## 4. Hybrid AI Architecture: Local Model + API Key

This is a central requirement of the project.

Implement an intelligent AI provider layer that can use local and cloud models together instead of tightly coupling the application to one model.

### 4.1 Local AI mode

Use Ollama to connect to locally installed models.

The application should allow the user to:

- Check whether Ollama is installed and running.
- See which local models are available.
- Select a model for question generation, explanations, or answer evaluation.
- Configure a local model endpoint when necessary.
- Check model availability before starting an AI operation.
- Receive clear error messages when a model is missing or unavailable.
- Continue using non-AI functionality when local inference is unavailable.

Do not assume that a specific model is already installed. Detect available models and explain how to configure one.

Local mode should prioritize privacy, offline availability, and control over the user's data.

### 4.2 Cloud API mode

Allow users to provide their own API key for a supported cloud AI provider.

The settings should include:

- Provider selection.
- API key input with concealed characters.
- API endpoint where applicable.
- Model selection or model identifier.
- Connection test.
- API usage and error status.
- Clear indication of which provider is being used.

Store credentials securely using Windows-supported secure storage when available. Do not store API keys as plain text in application logs, exported settings, source code, or the SQLite database.

Never hard-code API keys. Never print them to the console or expose them in error reports.

### 4.3 Hybrid mode

Implement a hybrid routing strategy that combines local and cloud inference.

For example:

- Use the local model for routine question generation and basic explanations.
- Use the cloud model for more complex questions, nuanced written-answer evaluation, or difficult grading decisions when configured.
- Use deterministic Python functions for scoring objective questions whenever possible.
- Use specialized tools for mathematical calculations and other verifiable tasks.
- Fall back to the local model when the cloud provider is unavailable, if the requested operation can reasonably be completed locally.
- Let users override automatic provider selection for individual operations.

Allow the user to choose between:

**Local only:** All supported AI operations run locally.

**Cloud only:** AI operations use the configured cloud provider.

**Hybrid automatic:** The application selects the most appropriate available option.

**Manual selection:** The user explicitly chooses the provider or model.

The routing system must not switch providers invisibly when doing so materially changes privacy, cost, or capabilities. Inform the user when an operation will send data to a cloud provider, and allow them to cancel or exclude sensitive source material.

If the cloud API is unavailable, the application should remain usable. Explain which functions are unavailable or less capable rather than pretending that every task has succeeded.

## 6. Question Generation Engine

Build a question-generation system that creates diverse, meaningful, and appropriately difficult questions.

Support the following question formats:

1. Single-choice multiple-choice questions.
2. Multiple-select questions.
3. True/false questions.
4. Short-answer questions.
5. Fill-in-the-blank questions.
6. Numerical calculation questions.
7. Mathematical problem-solving questions.
8. Programming and code-analysis questions.
9. Essay and extended-response questions.
10. Case studies and scenario-based questions.
11. Matching questions.
12. Ordering and sequencing questions.

For suitable subjects, support a mix of question types within a single exam.

Each generated question should contain structured metadata, including:

- Question ID.
- Subject and topic.
- Question text.
- Question type.
- Difficulty.
- Available answer options, if applicable.
- Correct answer or grading reference.
- Explanation for the correct answer.
- Maximum points.
- Grading rubric, where necessary.
- Skills or learning objectives assessed.
- Source reference, if the question is based on uploaded study material.

Use structured output validation rather than relying on unrestricted free-form AI text. Validate that every question is complete, that its answer format is correct, and that its grading information is usable before adding it to an exam.

### Question quality control

The system must try to prevent:

- Duplicate or near-duplicate questions in the same exam.
- Ambiguous wording.
- Multiple correct answers when only one is intended.
- Incorrect answer keys.
- Distractors that are obviously implausible.
- Questions unrelated to the selected topic.
- Difficulty that contradicts the selected level.
- Missing diagrams, code snippets, formulas, or context required to answer a question.
- Questions that cannot be graded using the selected evaluation method.

Where practical, validate generated questions against deterministic rules, calculations, tests, or a second independent evaluation pass.

Do not claim that an AI-generated question is verified when it has not been checked. Flag uncertain questions for review and let users edit or regenerate them before the exam begins.

## 7. Importing Study Materials and Creating Source-Based Exams

Allow users to provide their own study materials so the application can create exams based on what they are actually expected to learn.

- Pasted text.

Add a document import interface with file selection, processing status, extracted-text preview, and clear error reporting.

The application should:

1. Extract readable content.
2. Preserve document or page references where possible.
3. Identify relevant subjects, topics, definitions, and learning objectives.
4. Allow the user to choose which sections or topics to include.
5. Generate exam questions from the selected material.
6. Associate questions with their source sections or pages when traceable.
7. Avoid pretending that missing, unreadable, or image-only content has been processed correctly.

Use appropriate local parsing tools for document extraction. For scanned PDFs, make OCR an optional capability and clearly indicate when OCR is needed.

Support source-based exam generation in both local and cloud modes where technically feasible. Keep uploaded materials local by default. Before sending source text or derived content to a cloud model, inform the user and respect their selected privacy settings.

Treat imported files as untrusted data. Text inside a document must not be allowed to override the application's instructions, disclose credentials, execute commands, or change security settings.

## 8. Realistic Examination Interface

Create a dedicated exam-taking interface separate from the setup and results screens.

The interface should include:

- Current question and question number.
- Total number of questions.
- Visible countdown timer.
- Answer input appropriate to the question type.
- Previous and Next navigation.
- A question navigation panel.
- Clear status indicators for answered, unanswered, and flagged questions.
- A button to flag a question for later review.
- A progress indicator.
- A confirmation dialog before final submission.
- Automatic saving of answers during the exam.
- Recovery from an accidental application restart where feasible.
- A clear indication when the exam has been submitted or time has expired.

The user should be able to navigate questions without losing answers.

The timer must be based on reliable time tracking rather than only decrementing a visual counter. Persist the deadline so that restarting the application does not accidentally grant extra time.

When the duration expires, automatically close the exam and submit the answers according to the exam's configured rules. Clearly handle any answer that could not be saved.

Support a distraction-reduced full-screen mode. However, do not claim that the application can prevent cheating or guarantee a secure examination environment. Any optional monitoring or restricted-mode capabilities must be clearly described and implemented in a transparent, privacy-conscious way.

## 9. Exam Grading and Evaluation Engine

Implement a dedicated grading subsystem. Do not rely entirely on a language model to calculate scores.

### 9.1 Objective questions

Grade multiple-choice, true/false, matching, ordering, and other objective formats using deterministic answer keys and configurable scoring rules wherever possible.

Handle unanswered questions, partial credit, multiple correct answers, and negative marking according to the selected exam configuration.

Keep scoring logic separate from the interface and AI provider layer.

### 9.2 Mathematical and numerical questions

Support configurable numerical tolerance and units where appropriate.

Use reliable calculations and mathematical tools where applicable, rather than comparing numerical answers only as strings.

For complex mathematical problems, allow partial credit for intermediate steps when the grading rubric supports it. Distinguish a minor arithmetic error from a fundamental conceptual error where there is enough evidence to do so.

Do not mark mathematically equivalent expressions as incorrect merely because they use a different valid representation.

### 9.3 Programming questions

For programming questions, support grading criteria such as:

- Correctness of the output.
- Passing predefined test cases.
- Edge-case handling.
- Algorithmic reasoning.
- Code quality, if included in the rubric.
- Explanation of the proposed solution.

Where code execution is enabled, use a restricted execution environment with resource limits and no unnecessary access to the user's files, network, credentials, or operating system. Never run arbitrary user-submitted code directly with unrestricted permissions.

If a secure execution environment is unavailable, evaluate the code statically or ask the user to run it themselves, and clearly state the limitation.

### 9.4 Essay and open-ended questions

For written answers, use a rubric-based evaluation process.

The grading rubric should define:

- Expected concepts.
- Required facts, methods, or arguments.
- Weight of each criterion.
- Acceptable alternative answers.
- Common misconceptions.
- Conditions under which partial credit is awarded.

The AI should evaluate the substance of the answer, not just keyword overlap.

The grading process should distinguish between factual correctness, reasoning, completeness, clarity, and relevance when those dimensions are part of the rubric.

Return a structured grading result that includes the awarded points, maximum points, criteria scores, explanation, and confidence or review status.

For important assessments, allow the user to inspect and override AI grading decisions. The application must make it clear that AI evaluation can be imperfect, especially for open-ended questions.

### 9.5 Score calculation

Calculate the final score using deterministic application logic.

Show at least:

- Points earned.
- Maximum possible points.
- Percentage score.
- Passing status, if configured.
- Number of correct answers.
- Number of incorrect answers.
- Number of partially correct answers.
- Number of unanswered questions.
- Score breakdown by topic and question type.

Keep AI-generated explanations separate from the authoritative calculated score.

## 10. Detailed Post-Exam Analysis

After submission, display a comprehensive results dashboard.

The results should go beyond a percentage and a pass/fail label.

For each question, show:

- The original question.
- The student's answer.
- The correct answer or an example of an acceptable response.
- Points earned and maximum points.
- An explanation of the expected reasoning.
- Why the submitted answer received its score.
- The likely misconception or error, where identifiable.
- A recommended action for improvement.

Provide filters so the user can review all questions, incorrect answers, unanswered questions, or questions flagged during the exam.

For open-ended questions, display the grading criteria and explain which requirements were satisfied and which were missing.

If the evaluation is uncertain, explicitly label it as uncertain or in need of review rather than presenting a speculative judgment as fact.

## 11. Weakness Detection and Personalized Learning

Build a learning analytics component that identifies patterns across completed exams.

Track performance by:

- Subject.
- Topic and subtopic.
- Question type.
- Difficulty level.
- Type of error.
- Response time, where appropriate.
- Improvement across attempts.
- Confidence rating, if the user chooses to provide one.

Distinguish between a one-time mistake and a recurring weakness. Avoid drawing strong conclusions from a small amount of data.

Examples of useful insights include:

- The student understands the basic concepts but struggles with multi-step calculations.
- The student selects the correct formula but applies it incorrectly.
- The student understands a concept in multiple-choice questions but struggles to explain it independently.
- The student performs well on easy questions but loses accuracy as difficulty increases.
- The student repeatedly makes errors involving units, signs, definitions, or edge cases.

Use these findings to recommend which subjects, topics, and skills should be practised next.

Maintain a persistent learning profile locally, with controls that let users inspect, edit, reset, export, or delete their stored learning history.

## 12. Adaptive Exam Generation

Make the simulator capable of adjusting subsequent exams based on the student's history.

For example:

- If the student repeatedly makes errors in a topic, provide more targeted questions for that topic.
- If performance improves consistently, introduce harder questions.
- If the student performs well on basic questions but poorly on advanced ones, increase difficulty gradually.
- If a student struggles with a particular question format, provide additional practice in that format.
- If a student has already mastered a topic, reduce repetitive basic questions unless revision is requested.

Offer distinct modes:

**Fixed Exam:** Uses the difficulty and settings chosen by the user.

**Adaptive Exam:** Adjusts future questions based on the student's performance, within configured limits.

**Weakness Practice:** Focuses on the student's identified weak areas.

**Revision Exam:** Re-tests topics previously answered incorrectly.

**Mixed Mock Exam:** Combines previously studied topics and different question formats.

The adaptive system should explain why its recommendations were made and allow the user to override them.

Do not make the exam artificially easier just to improve the student's score. The objective is to measure and improve knowledge accurately.

## 13. Practice Mode and Learning Mode

In addition to realistic, timed exams, provide a separate practice mode.

Practice mode may offer:

- Immediate correctness feedback.
- Hints before revealing the answer.
- Step-by-step explanations.
- Links to relevant sections of imported study materials.
- Similar questions for additional practice.
- The option to retry an incorrect question.
- Optional confidence ratings.

The user should choose whether feedback is available after each question or only after the full exam.

In realistic exam mode, hide answers, grading details, and explanatory feedback until the exam has been submitted, according to the selected settings.

This separation is important: practice mode teaches the material, while exam mode measures the student's current performance.

## 17. Local Data Storage and Privacy

Store persistent data in a clearly defined application-data directory, using Windows conventions.

A logical structure might include:

- Application configuration.
- SQLite database.
- Imported study materials or references to source files.
- Exported reports.
- Optional diagnostic logs.
- Temporary processing files.

Use safe database operations and migrations when the schema changes. Handle interrupted writes and malformed records gracefully.

Privacy requirements:

- Keep data local by default.
- Do not send exam history or study materials to cloud services without informing the user.
- Let users select which AI operations are permitted to use cloud services.
- Avoid placing sensitive answer content in logs.
- Do not store API keys in ordinary plaintext configuration files.
- Provide clear controls for deleting, exporting, and backing up user data.
- Explain what is sent to a provider when cloud inference is used.
- Avoid sending an entire document when only a relevant excerpt is required.
- Do not transmit data in the background without a clear product purpose and appropriate user consent.

Make backup and restore functionality an optional but valuable feature.

## 18. Reliability, Error Handling, and Security

The application must handle common failure conditions without losing the student's work.

Account for:

- Missing local models.
- Ollama not running.
- Invalid API keys.
- API rate limits.
- Network interruptions.
- Provider outages.
- Malformed AI responses.
- Invalid generated questions.
- Document extraction failures.
- Database errors.
- Incomplete grading responses.
- Application restarts during an exam.
- Missing or changed source files.

Use explicit exception handling, structured logs, timeouts, retries with limits, and informative error messages.

Never silently convert an AI request failure into a fabricated success.

Validate all model-generated structured responses before using them in scoring or database operations.

Apply input validation to user-provided settings, file paths, exam configurations, and imported question sets.

Treat both uploaded documents and generated questions as untrusted content. Do not allow them to override system instructions, access secrets, or trigger arbitrary commands.

For any programming execution feature, implement a separately isolated and restricted execution mechanism. If reliable isolation is not available, disable execution by default and explain why.

## 21. Performance and Resource Management

The application must be usable on a typical Windows computer, with performance dependent on the selected local model and hardware.

Avoid loading large documents or AI models unnecessarily.

Use asynchronous or background execution for AI requests, lengthy document processing, and report generation where appropriate.

Display progress for lengthy operations and provide cancellation when safe.

Use pagination or incremental loading for large question banks and histories.

Do not assume that local inference is always faster or better than cloud inference. Allow the user to view the selected provider and explain when hardware or model limitations may affect response times.

Avoid requiring a powerful GPU for the core application. Select model recommendations according to the resources available, without promising that every model will run well on every computer.

Before writing the implementation, review the requirements and design the architecture. Identify dependencies, key data structures, provider interfaces, exam states, scoring rules, and the division between deterministic logic and AI-assisted evaluation.

Then implement the system incrementally.

Important implementation rules:

- Write real, executable code.
- Do not provide pseudocode when working implementation is reasonably achievable.
- Do not leave essential functions as `TODO`, `pass`, or simulated success responses.
- Do not assume the user has a particular local model installed.
- Do not require an API key for basic functionality.
- Do not hard-code provider credentials.
- Do not let a language model be the sole authority for objective scoring.
